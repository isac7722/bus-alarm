## 목표와 범위

**버스 번호 검색 → 목적지 방향 선택 → 지도 또는 목록에서 정류장 선택 → 같은 정류장 노선 최대 4개 저장**을 실제 iOS 앱에 구현한다. 기존 사용자는 저장된 설정 화면으로 진입하고, 신규 사용자와 편집 사용자에게 새 흐름을 제공한다. 기존 정류장 검색도 유지한다.

기술 기준은 현재 저장소의 Go 백엔드, PostgreSQL·Redis, iOS 17 이상 SwiftUI·WidgetKit·ActivityKit이다. 지도는 MapKit을 우선 검증한다. HTML 시안의 지도·노선·방면 예시는 실제 데이터로 교체한다.

이 작업에서 길찾기, 하차 알림, 실시간 차량 지도, 여러 정류장 저장은 추가하지 않는다. 현재의 한 정류장·최대 4개 노선 규칙 안에서 선택 경험과 방향 정확도를 개선한다.

## 코드에서 확인한 선행 문제

| 현재 상태 | 구현에 미치는 영향 |
|---|---|
| `http.go`는 정류장 검색·상세·도착정보와 Live Activity 제공 | 노선 검색, 방향별 경유 정류장, 지도 경로 API 필요 |
| `Route`/`RouteSummary`에 노선 ID와 이름만 있음 | 지역·유형·기종점·방향·경유 순번 모델 필요 |
| `gyeonggi.go`는 반복 경유의 도착정보를 노선 ID별로 합침 | 지도에서 고른 방향을 별도 도착 조회까지 전달해야 함 |
| `regional.go`는 제공기관의 노선 ID를 같은 맵에서 합침 | 새 모델은 제공기관을 구분하고, 동일 노선 여부는 검증된 매핑으로만 판단 |
| `WidgetConfigurationData`는 정류장·노선 ID만 저장 | 경유 순번/방향을 담는 새 선택 모델과 이전 설정 읽기 필요 |
| `AppGroupStore`의 도착 캐시는 하나의 키에 저장 | 정류장·방향 변경 후 과거 캐시가 표시되지 않도록 선택별 검증 필요 |
| DB `stations.station_id`는 5자리, `routes.route_id`는 9자리 | 새 접두어 ID를 기존 테이블에 그대로 넣을 수 없음 |
| `make restart`는 backend만 재생성 | 기존 CSV/Excel 데이터를 다시 가져오는 배포 절차를 사용하지 않아야 함 |

**방향에 맞는 도착정보 검증이 지도 UI보다 먼저 완료되어야 한다.** 경기도 공식 도착정보 항목조회에는 `stationId`, `routeId`, `staOrder`가 있으며, 같은 정류장에서 양방향이 정차하는 경우 순번이 필요하다고 명시되어 있다. 이를 새 흐름의 기본 조회 단위로 사용한다. [GBIS 공식 문서](https://www.gbis.go.kr/gbis2014/publicService.action?cmd=mBusArrival)

## 1단계 — 실제 데이터와 식별 규칙 검증

작업:

- 서울·경기 **노선 조회** 서비스 활용 승인과 정상 응답 확인. 기존 정류소·도착정보 승인만으로 노선 조회가 된다고 가정하지 않는다.
- 9304번과 강변역 05267을 기준으로 노선 검색 → 경유 정류장 → 방향·순번 → 해당 순번의 도착정보까지 연결한다.
- 일반 서울 노선, 동명 반대편 승강장, 같은 번호의 다른 지역 정류장, 순환·회차·반복 경유 노선을 표본에 포함한다.
- 서울의 순번 기반 도착 조회 방식과 응답의 식별 필드를 확인한다. 방향 문구·노선 순번만 보고 다른 제공기관의 순번과 동일시하지 않는다.
- 같은 물리적 정류장과 같은 노선이 두 제공기관에 나타나는 경우 매핑 근거를 기록한다. 표시 번호·이름·좌표 근접성만으로 병합하지 않는다.
- API 키 없는 응답 fixture와 정규화 예상 결과를 저장한다. 실제 호출은 별도 진단 기능으로 분리한다.

산출물: 제공기관별 필드 매핑, 승인 확인 결과, fixture, 방향 판정 규칙, 지원 불가 사례와 이유.

완료 기준: 9304/05267의 실제 선택을 하나의 정류장·노선·방향·경유 순번으로 설명할 수 있고, 그 조합으로 도착정보를 조회할 수 있다. 문서 확인과 인증키를 사용한 실호출 결과를 구분해 기록한다.

공식 서비스:

- [서울특별시 노선정보조회 서비스](https://www.data.go.kr/data/15000193/openapi.do)
- [경기도 버스노선 조회](https://www.data.go.kr/data/15080662/openapi.do)
- [경기도 경유정류소 목록조회](https://www.gbis.go.kr/gbis2014/publicService.action?cmd=mBusRouteStation): `stationSeq`, `turnSeq`, `turnYn`, 좌표 등을 제공한다. 실제 방향 그룹 구성은 표본으로 검증한다.

승인 대기 중에는 fixture 기반 서버·앱 개발을 진행할 수 있다. 실제 데이터 검증 전에는 새 기능을 운영에서 활성화하지 않는다.

## 2단계 — 노선 탐색 API와 데이터 모델

### 식별자와 저장 전략

- 신규 API는 제공기관을 포함한 `route_ref`, `station_ref`를 사용한다. 예: `seoul:<공급기관 ID>`, `gg:<공급기관 ID>`. 내부 기술 식별자는 앱 화면에 표시하지 않는다.
- `station_ref`는 물리적 승강장, `boarding_id`는 **노선 + 승강장 + 해당 경유 순번**을 식별한다. 반복 경유를 정류장 ID만으로 제거하지 않는다.
- 서버는 선택 시점의 `route_revision`을 함께 반환한다. 노선 개편으로 순번 의미가 바뀌면 이전 선택을 다른 방문으로 자동 재해석하지 않고 재선택을 요구한다.
- 기존 `05267`, `gg:...`, 기존 노선 ID 및 v1 응답은 그대로 둔다. 새 식별자를 기존 5자리/9자리 DB 컬럼에 저장하지 않는다.
- 첫 구현은 **공공 API 조회 + Redis 캐시**를 사용하고 전국 노선을 DB에 일괄 적재하지 않는다. 새 API의 정류장은 기존 CSV에 없더라도 제공기관 정류장 조회로 해석 가능하게 만든다.
- 기존 설정과의 연결은 DB의 node ID 및 검증된 제공기관 매핑으로 처리한다. 매핑이 모호한 기존 설정은 유지하고 다음 편집 때 재선택하게 한다.

### API 초안

기존 클라이언트가 새 방향 정보를 무시하는 일을 방지하기 위해 새 흐름은 `/api/v2`로 분리한다. 아래는 구현할 계약 초안이며 현재 제공되는 API가 아니다. 1단계 결과로 필드 의미를 확정한 뒤 서버와 앱이 같은 계약을 사용한다.

| API | 용도 / 핵심 응답 |
|---|---|
| `GET /api/v2/capabilities` | 새 탐색 가능 여부, 제공기관별 지원 상태 |
| `GET /api/v2/routes/search?q=9304` | `route_ref`, 번호, 지역, 유형, 기종점, 조회한 제공기관의 성공/실패 상태 |
| `GET /api/v2/routes/{route_ref}` | 방향 그룹, 순서 있는 정류장, `boarding_id`, 좌표, 다음 정류장, 선택 가능 여부, `route_revision` |
| `GET /api/v2/routes/{route_ref}/geometry` | 경로 좌표, 좌표 출처, 실제 경로/정류장 연결선 구분; 지도와 독립적으로 실패 가능 |
| `GET /api/v2/stations/{station_ref}/boarding-options` | 같은 승강장을 지나는 전체 노선과 각 노선의 방향·경유 선택지 |
| `POST /api/v2/selections/validate` | 같은 정류장·최대 4개·최신 노선 관계를 검증하고 저장할 정규화 선택 반환; 서버 영속 저장 없음 |
| `POST /api/v2/arrivals` | 검증 가능한 선택 조합으로 방향별 도착정보 조회; 본문은 정류장 및 1~4개 탑승 선택 |
| `POST/DELETE /api/v2/live-activities` | 동일한 탑승 선택으로 대기 등록/종료; 기존 인증·수명 제한 유지 |

`boarding_id`나 클라이언트가 전송한 방향 텍스트는 신뢰하지 않는다. 서버에서 최신 노선·정류장·순번 관계를 확인하고, 다른 정류장의 노선 혼합·중복·초과 선택을 거부한다. 신규 선택은 한 노선당 한 경유 선택만 허용한다.

새 검색은 한 제공기관 장애 시 성공한 검색 결과와 누락 상태를 함께 반환할 수 있다. 다만 최종 ‘같은 정류장의 전체 버스’ 목록은 필요한 제공기관을 모두 확인하기 전 완전한 목록으로 표시하지 않는다. 오류와 실제 결과 없음도 구분한다.

캐시는 검색·노선·경로와 도착정보의 TTL을 분리한다. 현재 `Cache.Set`은 공통 TTL이므로 별도 메타데이터 캐시 인터페이스를 추가한다. 초기 제안값은 검색 5분, 노선/경로 1시간이며 실제 갱신 주기·호출 한도에 따라 조정한다. 조회 병합과 제한된 동시 호출로 반복 탭에 따른 API 호출 증가를 막는다.

변경 후보: `http.go`, `service.go`, `types.go`, `config.go`, `cache.go`, `regional.go`, `repository.go`; 신규 `route_catalog.go`, `route_catalog_test.go`와 제공기관별 노선 어댑터.

완료 기준: 지도 없이도 API만으로 노선 검색, 방향 선택, 정류장 선택, 추가 노선 검증을 끝낼 수 있다. 기존 v1 호환성 테스트가 통과한다.

## 3단계 — 방향별 도착정보와 Live Activity

- 경기도는 항목조회에 `staOrder`를 전달하고, 응답의 정류장·노선·순번 일치를 검사한다. 서울도 검증된 순번 기반 조회로 연결한다.
- 기존 v1 노선 단위 합산은 유지하되 v2에서는 다른 경유 순번의 도착정보를 합치지 않는다.
- 도착 캐시 및 요청 합치기 키에 제공기관·정류장·노선·경유 순번·계약 버전을 포함한다.
- Live Activity 등록, Redis 세션, 주기적 조회, 차량 추적 모두 동일한 탑승 선택을 사용한다. 노선은 같지만 방향이 달라진 등록을 같은 대기로 처리하지 않는다.
- 노선 변경 또는 공급기관의 순번 불일치 시 도착 예상치를 만들지 않는다. 명확한 재선택/조회 불가 상태로 응답한다.
- API가 반복 경유를 구분할 수 없는 사례는 서버에서 `selectable=false`와 사유를 제공한다. 테스트를 통과한 사례부터 지원하며 미지원 범위는 출시 기록에 남긴다.
- 기존 사용자의 진행 중 대기는 유지한다. 위젯 설정을 편집했다고 대기 중인 버스가 바뀌지 않는다. 다른 버스로 대기를 시작할 때 기존 대기 종료 흐름을 적용한다.

변경 후보: `gyeonggi.go`, `upstream.go`, `regional.go`, `live_activity.go`, `live_state.go`, `service.go`와 관련 테스트.

완료 기준: 같은 노선·같은 정류장·다른 순번에 대해 위젯 조회와 Live Activity가 각각 선택한 방향의 차량만 반환한다. 기존 APNs 동작과 오래된 세션 복원이 유지된다.

## 4단계 — iOS 공유 모델과 저장 호환성

- `RouteCatalogSummary`, `RouteDirection`, `RouteStopOccurrence`, `BoardingSelection` 모델과 APIClient의 v2 메서드를 추가한다.
- `WidgetConfigurationData`에 버전과 선택 정보를 추가한다. 기존 `stationId`, `stationName`, `routeIds`는 이전 설정 디코딩을 위해 유지하며, 새 저장 경로는 `station_ref`와 선택 배열을 기준으로 동작한다.
- 구버전 JSON은 v1 조회로 계속 동작하게 한다. 앱 실행만으로 방향을 추정해 자동 변환하지 않는다. 사용자가 새 흐름에서 저장할 때 v2 설정으로 전환한다.
- v2 설정에서 v1 정보가 없거나 불완전할 수 있으므로 이전 필드는 선택적으로 읽고 버전별 필수 필드를 검증한다. 알 수 없는 버전/손상된 선택은 다른 버스의 도착정보로 대체하지 않는다.
- `ConfigurationDraft`가 검색어·선택 노선·방향·정류장·추가 버스를 관리한다. 화면 전환과 서버 재조회가 초기 선택을 반복해서 덮어쓰지 않게 한다.
- 서버 검증 성공 후 App Group 저장 → 위젯 갱신 순으로 처리한다. 실패·취소하면 기존 설정을 보존한다.
- 도착 캐시에 설정 식별값을 함께 저장한다. 위젯의 snapshot·timeline·네트워크 실패 경로 모두 현재 정류장·노선·순번과 일치하는 캐시만 사용한다.
- `BusWaitingManager`, `LiveWaitStore`, `BusWaitingAttributes`에 선택 정보를 전달한다. 이전 ActivityKit attributes와 저장 레코드도 읽을 수 있도록 선택적 필드로 확장한다.
- 저장 화면의 정류장 번호는 식별자 문자열을 잘라 만들지 않고 표시용 번호를 사용한다. 버스별 방면도 표시한다.

변경 후보: `ios/Shared/Models/StationModels.swift`, `WidgetConfigurationData.swift`, `ArrivalModels.swift`, `BusWaitingAttributes.swift`, `APIClient.swift`, `AppGroupStore.swift`, `BusWidgetProvider.swift`, `BusWaitingManager.swift`, `LiveWaitStore.swift`, `SavedConfigurationView.swift`.

완료 기준: 이전 설정과 캐시로 앱·위젯이 열리고, 새 설정 저장·앱 재시작 후에도 방향이 유지된다. 다른 선택의 오래된 캐시가 표시되지 않는다.

## 5단계 — SwiftUI 화면 구현

| 구성요소 | 구현할 행동 |
|---|---|
| `BusSearchView` / ViewModel | 버스/정류장 검색 전환, 최근 검색은 기기 내 저장, 300ms debounce, 취소·오래된 응답 폐기, 지역·기종점 표시 |
| `RouteMapSelectionView` / ViewModel | MapKit 노선선과 핀, 방향 선택, 선택 방향만 강조, 카메라 상태 보존 |
| `RouteStopListView` | 방향별 노선 순서 목록, 지도와 같은 `boarding_id` 선택 상태 |
| `StationSelectionSheet` | 전체 이름·번호·방향·다음 정류장, 접기/펼치기, 명시적 확인 버튼 |
| `LocationService` | ‘내 위치’ 탭 후 사용 중 위치 권한 요청, 거절/정확도 부족 처리, 지속 추적 없이 필요 시 위치 조회 |
| `RouteSelectionView` 확장 | 처음 찾은 노선 사전 선택, 같은 정류장의 추가 노선, 각 노선의 방향 확인, 최대 4개 |
| `RootView` 편집 흐름 | 기존 홈 유지, 새 사용자 검색 진입, 뒤로 이동 시 초안 보존, 편집 취소와 최종 저장 구분 |

구체적 규칙:

- 방향 미선택 시 정류장 확정 불가. 방향 변경은 호환되지 않는 선택을 해제한다.
- 같은 정류장 반복 경유는 목록에서 순서·방향·다음 정류장으로 구분한다. 지도 핀이 겹치면 목록 선택으로 연결한다.
- 처음에는 노선 전체를 보여주고, 정류장 선택 시 지도가 해당 위치로 이동한다. 지도 이동만으로 선택을 바꾸지 않는다.
- 위치 거절과 지도 표시 실패에도 목록으로 저장할 수 있다. 좌표 없는 정류장은 목록에는 남기고 가짜 좌표를 만들지 않는다.
- 실제 경로 데이터가 없으면 연결선임을 명시하거나 정류장 핀만 보여준다. 형상 조회 실패가 목록 선택을 막지 않는다.
- 기존 정류장 검색 진입 시 선택한 정류장을 유지한 채 노선·방향을 고른다. HTML 시안처럼 정류장 선택을 버리고 예시 노선으로 넘기지 않는다.
- 정류장 기반 검색 결과를 v2에 연결할 때도 node ID/제공기관 매핑을 검증한다. 매핑 불가 시 기존 설정 흐름을 제공하며 방향 보장을 암시하지 않는다.
- API가 정상이고 도착 예정 차량만 없는 경우 정류장·노선 저장은 허용한다.
- 기본 17pt와 Dynamic Type, 44pt 터치, 안전 영역, VoiceOver, 동작 줄이기, 어두운 모드를 반영한다. 큰 글씨에서는 확장된 목록을 우선한다.
- `ios/project.yml`에 사용 중 위치 권한 설명을 추가하고 XcodeGen으로 프로젝트를 갱신한다. 정류장 중심 탐색으로 확장하면서 지도 범위를 서버로 전송한다. 실제 반영 계약은 route-map-api.md를 따른다. 실제 데이터 처리에 맞춰 앱 내 개인정보 문서와 App Store 정보를 점검한다.

완료 기준: 실제 데이터로 검색부터 저장까지 완료하고, 위치 권한 없이도 같은 작업이 가능하다. 위젯·Live Activity에서 지도에서 선택한 방향을 확인할 수 있다.

## 6단계 — 회귀 검증과 서버·앱 반영

필수 시나리오:

1. **9304 검색 → 강변역 05267 선택 → 올바른 실제 방면 확인 → 저장 → 위젯과 대기 시작**.
2. 같은 05267 번호를 가진 다른 지역 정류장과 혼동되지 않음.
3. 방향 변경, 반대편 승강장, 같은 정류장 반복 경유에서 다른 방향의 도착정보가 섞이지 않음.
4. 초기 노선 사전 선택, 최대 4개 제한, 도착정보 없는 경유 노선도 목록 유지.
5. 검색 연타, 뒤로 가기, 로딩 중 취소, API 오류/쿼터 초과, 노선 변경 시 선택·기존 설정 보존.
6. 위치 거절, 지도 실패, 좌표 없음, 최대 Dynamic Type와 VoiceOver로 설정 완료.
7. 이전 앱 설정 디코딩, 기존 v1 API, 이전 Live Activity 세션 복원, 새 설정의 선택별 캐시 검증.

자동화는 제공기관 응답 fixture와 실제 경계 조건에 집중한다. 운영 API를 매번 호출하는 테스트는 기본 테스트에서 제외하고 별도 진단으로 실행한다.

현재 사용할 수 있는 검증 명령:

```bash
# Ubuntu / macOS: Docker에서 백엔드·DB·Redis 검증
make test-backend

# macOS + Xcode: 설치된 시뮬레이터 이름 지정
make test-ios SIMULATOR="iPhone 17 Pro"
```

추가할 Make 대상(아직 없음):

- `make routes-check`: 노선 서비스 승인·연결과 9304/05267의 식별·순번 조회 확인. API 키 비노출, DB 쓰기 없음.
- `make routes-smoke`: 실행 중인 백엔드의 새 API로 검색 → 정류장 → 선택 검증 → 도착정보 확인. APNs 전송이나 실제 대기 등록은 하지 않음.

반영 순서:

1. 로컬·검증 환경에서 백엔드 신규 API와 기존 v1 호환성을 통과시킨다.
2. 실제 서빙 서버에 백엔드를 먼저 배포한다. APNs 서버는 기존 설정대로 `make restart APNS=1`, 이후 `make wait-server` 및 새 API smoke 확인. health 성공만으로 노선 연동 성공을 판단하지 않는다.
3. 첫 구현은 노선 DB 일괄 적재·CSV 재반영·기존 카탈로그 삭제가 필요 없는 구조로 진행한다. 노선 목록 때문에 `make stations-update`를 반복 실행하지 않는다.
4. TestFlight에서 실제 지도·위젯·Live Activity를 검증한 뒤 앱에 노출한다. 서버 capability가 없으면 기존 탐색 흐름을 제공한다.
5. 문제가 생기면 신규 설정 진입부터 비활성화한다. 이미 저장된 v2 설정을 지원하는 서버는 유지한다. v2를 모르는 서버로 되돌리고 방향 없는 v1 도착정보로 대체하지 않는다.
